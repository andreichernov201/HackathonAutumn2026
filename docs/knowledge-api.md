# База знаний Regula AI

Модуль встроен в существующий FastAPI (`api.main:app`) и использует **ту же** SQLite `REGULA_DATA_DIR/documents.sqlite3`, подписанную сессию и CSRF-защиту, что и сервис документов. Второй backend, отдельная база для AI, внешние AI API и векторная инфраструктура не создавались.

## Реальный корпус

В `api/knowledge/sources/` включены побайтовые копии трёх файлов, предоставленных пользователем:

| Файл в репозитории | Материал | Структура после извлечения |
| --- | --- | --- |
| `records-instruction.pdf` | Инструкция по ДОУ и документообороту | 51 страница, главы, пункты и приложения |
| `approval-matrix.docx` | Матрица обязательного визирования | таблица, группы внутренних/внешних документов, отдельные строки |
| `modular-guidance.docx` | Методические рекомендации по модульным документам | разделы и пункты, включая 2.1 |

`manifest.json` содержит исходные имена, SHA-256 и постоянные идентификаторы. При запуске три оригинала импортируются идемпотентно. Повторный старт не создаёт новых редакций. `REGULA_IMPORT_CASE_CORPUS=0` отключает стартовый импорт; уже импортированные данные не удаляет. Сравнение checksum защищает bundled-корпус от незаметной подмены.

Материалы **синтетические учебные**, не действующие нормативные акты Банка России. Дата утверждения внутри учебного примера не принимается за подтверждение применимости. Редакция и даты действия не установлены; статус всех трёх импортов — `unverified`. Значения не придуманы.

Семь предоставленных DOCX-модулей имеют те же SHA-256, что `api/templates/sources/` из ветки документов. Они остаются в едином существующем каталоге `/api/document-templates`; повторного нормативного импорта нет. Новые материалы категории `template` можно загрузить в базу знаний, но обычный нормативный поиск их исключает. Для поиска шаблонов явно укажите `category=template` или `includeTemplates=true`.

## Запуск и загрузка

```sh
cp .env.example .env
# Задайте длинный случайный REGULA_SESSION_SECRET.
# Для обслуживания задайте REGULA_KNOWLEDGE_ADMIN_TOKEN длиной минимум 32 символа.
docker compose up --build
```

Откройте `http://127.0.0.1:8080/#knowledge`. Сразу доступны три исходных материала и поиск. Для загрузки новых документов: «Управление базой» → ключ оператора → «Загрузить документ». В просмотрщике доступна «Новая редакция». Ключ хранится на сервере; frontend его не сохраняет в localStorage. Пустая настройка ключа отключает обслуживание.

Для разработки:

```sh
python3 -m venv .venv
.venv/bin/pip install -r api/requirements.txt
export REGULA_SESSION_SECRET='replace-with-random-development-secret'
# При необходимости export REGULA_KNOWLEDGE_ADMIN_TOKEN='your-random-key-at-least-32-characters'
.venv/bin/uvicorn api.main:app --host 127.0.0.1 --port 8000 --reload
# В другом терминале:
npm ci
npm run dev
```

Сайт: `http://127.0.0.1:5173/#knowledge`. API-документация: `/api/docs`, OpenAPI: `/api/openapi.json`. Создавайте резервную копию всего `REGULA_DATA_DIR`, включая SQLite и оригиналы. Не удаляйте Docker volume, если нужно сохранить ссылки.

## API

Все запросы проверяют разрешённый уровень доступа через `KnowledgeService`. Недоступный документ/пункт возвращает `404` без метаданных источника. Каталог и поиск фильтруются **до** подсчёта и пагинации.

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/api/knowledge/session` | Роль, явный demo-режим, доступность обслуживания |
| POST / DELETE | `/api/knowledge/admin-session` | Вход по ключу оператора / завершение обслуживания |
| GET | `/api/knowledge/documents` | Каталог, фильтры `category`, `status`, `fileType`, `sort`, `limit`, `offset` |
| GET | `/api/knowledge/documents/{id}` | Метаданные и последняя загруженная редакция |
| GET | `/api/knowledge/documents/{id}/versions` | Все сохранённые редакции с пагинацией |
| POST | `/api/knowledge/documents` | Новый документ: multipart `file` + JSON-строка `metadata` |
| POST | `/api/knowledge/documents/{id}/versions` | Добавление редакции; предыдущие оригиналы сохраняются |
| GET | `/api/knowledge/versions/{id}/sections` | Структура: `items`, `total`, `limit` (до 1000), `offset` |
| GET | `/api/knowledge/sections/{id}` | Точный извлечённый текст, таблица, проверяемый источник |
| GET | `/api/knowledge/search?q=...` | Полнотекстовый поиск, фильтры и `versionId` |
| GET | `/api/knowledge/versions/{id}/original` | Оригинал после проверки доступа и SHA-256 |
| POST | `/api/knowledge/versions/{id}/index` | Переиндексация неизменных пунктов |
| GET | `/api/knowledge/tools` | Шесть разрешённых инструментов с JSON Schema входа/выхода |
| POST | `/api/knowledge/tools/{name}/invoke` | `{ "arguments": {...} }`, те же сервисы и полномочия |
| GET | `/api/knowledge/audit` | Журнал импортов/редакций и переиндексации, только администратор |

Каталог/поиск: `limit` 1–100 (по умолчанию 20), `offset` 0–100000. Редакции: до 100 на запрос. Сортировка каталога: `title`, `createdAt`, `updatedAt`; поиск сортируется BM25. Статус `active` фильтрует также подтверждённые даты действия на серверную календарную дату. Последняя загрузка и применимая редакция — разные понятия; без фильтра каталог показывает последнюю загруженную, поиск явно указывает редакцию каждого совпадения.

Пример метаданных загрузки:

```json
{
  "title": "Название оригинального документа",
  "category": "instruction",
  "description": "Описание",
  "accessLevel": "internal",
  "materialNature": "synthetic",
  "status": "unverified",
  "versionLabel": null,
  "effectiveFrom": null
}
```

Категории: `instruction`, `matrix`, `guidance`, `template`, `other`. Доступ: `internal` (читатели демо) / `restricted` (только администраторы базы). Подтверждённые статусы `active`/`archived` требуют `statusEvidence`; `active` требует `effectiveFrom`. Допустим `effectiveUntil`. Переименование/смена ACL/классификации через добавление редакции запрещены. Повторный checksum внутри документа возвращает `409` и не затрагивает старый оригинал.

Перед изменением получите `GET /api/session` и передайте `X-CSRF-Token: csrfToken`. Сохраните полученную HttpOnly cookie. Общий frontend-клиент выполняет bootstrap сессии один раз, до параллельных запросов; документы и база знаний используют один механизм. Все вызовы инструментов требуют CSRF, даже если инструмент только читает.

## Структура и достоверность

- `knowledge_documents` — каталог, классификация, синтетическое происхождение, уровень доступа.
- `knowledge_versions` — checksum, исходное имя и формат, неизвестные/подтверждённые метаданные редакции, извлечение и индексация.
- `knowledge_sections` — логическая иерархия, нумерация, точный извлечённый текст, структурированная таблица, диапазон PDF-страниц.
- `knowledge_chunks` — отдельные перекрывающиеся RAG-фрагменты с привязкой к пункту; `embedding_status=not_configured`.
- `knowledge_fts` / `knowledge_fts_ru` — SQLite FTS5: исходный текст для точных фраз и локальный русский Snowball для форм слов.
- `knowledge_audit` — оператор, действие, документ, редакция, checksum/основание статуса, время.
- `knowledge_migrations` — воспроизводимые SQL-миграции; миграция 002 добавляет русский индекс и перестраивает его из сохранённых пунктов.

Номер пункта не заменяется случайным RAG-фрагментом. Если логический номер не распознан, это явно `locatorConfidence=fragment`. Постоянная ссылка: `/#knowledge/sections/{sectionId}`. В составе цитаты всегда есть `documentId`, `versionId`, `sectionId`, `locator`, `excerpt`, `sourceReference`, `originalUrl`, `checksum`.

У загруженных документов идентификатор документа — UUID, идентификатор редакции получен из UUID документа и checksum; идентификатор пункта — из редакции и его позиции в зафиксированном извлечении. У трёх bundled-документов UUID задан manifest, поэтому чистые установки получают одинаковые ссылки. Переиндексация **не переразбирает оригинал**, не заменяет текст и не удаляет пункты: перестраивает только производные индексы/чанки. Изменение парсера для уже импортированного материала требует явного будущего процесса миграции извлечения; текущие ссылки не переназначаются.

PDF сохраняет страницы; повторяющаяся точная учебная маркировка исключена из текста пунктов с явным предупреждением, оригинальный файл сохранён целиком. Геометрическая сортировка текста не используется: она смешивает диагональную маркировку с пунктами. DOCX сохраняет порядок абзацев/таблиц; объединённые строки матрицы становятся группами, строки 1–N — отдельными источниками с заголовками колонок. Отметки «Да», «Нет» и текст условия сохраняются без пересказа. Это не фактический маршрут согласования.

Поиск без кавычек учитывает формы русских слов, объединяет токены по OR и ранжирует BM25; это поиск совпадений, а не семантическая проверка применимости. Точная фраза задаётся двойными кавычками. Нулевой результат сообщает об отсутствии подтверждённого основания по запросу. Оценка поиска не является вероятностью правильного ответа.

## Qwen/RAG

Разрешённые инструменты:

1. `list_knowledge_documents` (`ListArgs` → `DocumentPage`)
2. `search_knowledge` (`SearchArgs` → `SearchPage`)
3. `get_knowledge_document` (`DocumentArg` → `KnowledgeDocument`)
4. `get_knowledge_section` (`SectionArg` → `KnowledgeSection`)
5. `list_knowledge_versions` (`DocumentArg` → `VersionPage`)
6. `verify_citation` (`CitationArg` → `CitationVerification`)

`additionalProperties=false`; нельзя передать роль, SQL, путь файла или произвольное имя функции. Роль берётся из проверенной сервером сессии. Серверный оркестратор может вызывать те же методы напрямую с проверенным `Principal`, а не со словарём аргументов LLM.

Цепочка: `search_knowledge({q})` → `get_knowledge_section({sectionId})` → `verify_citation({documentId,versionId,sectionId,excerpt})`. Проверяются доступ, совпадение редакции, точное вхождение выдержки в сохранённый текст и checksum оригинала. Отказ/непроверенная цитата должны блокировать уверенное нормативное утверждение. Для применимой редакции используйте подтверждённые метаданные и при необходимости уточните дату пользователя.

Для подключения Qwen нужно реализовать серверный `/api/chat`, загрузить разрешённый tool registry, ограничить число/объём вызовов, валидировать возвращаемые цитаты и сформировать существующий `ChatResult`. `VITE_CHAT_BACKEND=api` уже переключает клиент на этот контракт; сам Qwen-оркестратор в этот PR не входит. `ChatRequest.context.knowledgeSource` фиксирует выбранный пункт/редакцию. `SourceReference` расширен совместимо, блок `citation` и `WorkspacePanel` сохранены; реальные источники открывают и панель, и пункт базы знаний.

Без Qwen обычный текстовый чат ищет в **той же реальной базе**, возвращает исходные выдержки и явно сообщает, что это поиск, а не AI-анализ. Действие «Спросить AI об этом пункте» закрепляет источник в контексте и предупреждает об отсутствии генеративного объяснения. Старые демонстрационные цитаты могут сохраниться в локальной истории, но новые нормативные вопросы не используют отдельный зашитый корпус.

Текст файлов и результаты инструментов — **недоверенные данные**. Они не исполняются, не становятся системными инструкциями, не меняют роль/набор инструментов и не дают модели доступ к SQL. Registry содержит эту маркировку. Будущий оркестратор обязан сохранить границу system/tool; один поиск не гарантирует защиту произвольной LLM от prompt injection.

## Безопасность и ограничения

Это явный **демо-режим**. Подписанная cookie разделяет устройства, но не подтверждает сотрудника организации. `internal` доступен читателям демо; `restricted` — локальному администратору. Админ-вход по серверному ключу — режим обслуживания, не корпоративная авторизация. Грант ограничен 8 часами и отзывается при смене ключа или выходе. Есть CSRF, ограничение попыток входа, аудит, no-store и nosniff. Для корпоративного развёртывания замените адаптер сессии на SSO и сопоставление групп с ACL, добавьте HTTPS/secure cookies и централизованный аудит. API в Compose не публикует порт наружу; web привязан к loopback.

Файлы до 20 МБ, только текстовые PDF, DOCX и UTF-8 TXT. Проверяются MIME, сигнатура и содержимое, предел распакованного DOCX, число страниц/секций и объём текста; запрещены макросы. Имя клиента не используется как путь. Оригинал хранится под идентификатором, открывается только после проверки доступа и checksum. Nginx ограничивает всё тело запроса 22 МБ; локальный API дополнительно проверяет Content-Length и фактический размер файла. Для публичного прямого API следует также ограничить chunked uploads на reverse proxy.

Не реализованы: OCR, XLSX, смысловой/векторный поиск, локальная embedding-модель, Qwen-оркестратор, сравнение редакций, корпоративный SSO и фактический обмен с ИИС ДО. DOCX-страницы не выдумываются. Автоматическая Word-нумерация без явного текста получает предупреждение; для других сложных документов точность нужно проверять по оригиналу. PDF-таблицы показаны извлечённым текстом с привязкой к странице, без обещания сохранения их геометрии. Индексация синхронная, ограничена размером MVP; очередь обработки не реализована. Официальный статус учебного корпуса не подтверждён.

## Проверки

```sh
.venv/bin/python -m pytest -q api/tests
npm run build
```

Тесты покрывают исходный сервис документов, загрузку PDF/DOCX/TXT, фразы/номера/русские формы, выдачу и пагинацию, неизвестное основание, матрицу с обязательными/условными колонками, точный checksum, старые редакции/ссылки, переиндексацию, исходные файлы, CSRF и ACL для всех путей и AI-инструментов. `test_case_corpus.py` отдельно проверяет именно пользовательские оригиналы: 51 страницу PDF, п. 2.1 рекомендаций первым результатом и строку 6 внутренних документов первым результатом вопроса об ИТ-проекте. Сгенерированные фикстуры используются только в изолированных тестах.

## Поиск метаданных каталога (этап 02)

`GET /api/knowledge/documents?q=...` дополнительно поддерживает буквальный поиск подстроки по названию, описанию и владельцу документа без учёта регистра, включая кириллицу. Необязательный `q` ограничен 500 символами; пустая строка сохраняет поведение каталога. ACL, статус, формат, категория, сортировка и серверная пагинация применяются как прежде. Это отдельная выдача документов; поиск по пунктам и морфология остаются в `/api/knowledge/search` (FTS5). SQL-параметры связаны, символы `%` не становятся шаблоном.

Интерфейс и проверенные сценарии описаны в [отчёте этапа 02](knowledge-workspace.md).
