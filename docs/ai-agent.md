# Regula AI: серверный агент и формы в чате

## Реализация и статус проверки

Рабочая ветка начата от `main` `b22afdb5b841052c2b342e983c66c8282c1d0cdc`.
Проверены актуальные модели и общий реестр; открытых PR на момент начала не было.

`api/agent/` содержит `AIProvider`, HTTP-адаптеры `DeepSeekProvider` и
`LocalQwenProvider`, `AgentRunner`, строгие контракты, системную инструкцию,
серверную историю и журнал исполнения. `POST /api/chat` выполняет последовательные
Function Calling через **существующий** `api/tool_registry.py`. Нового хранилища
документов, реестра инструментов или RAG-базы нет.

Основная модель — только `deepseek-v4-pro`, endpoint `https://api.deepseek.com`.
Автоматического переключения на Flash нет. Провайдер использует официальный
Chat Completions API. В thinking mode `reasoning_content` сохраняется в закрытом
серверном transcript и возвращается в последующие запросы с tools, включая
сохранённые предыдущие полные ходы. В публичной истории, статусах, ответах и логах
рассуждений нет. При сокращении контекста удаляются только целые старые ходы.

Источники контракта провайдера, проверенные 25 октября 2026:
[thinking mode](https://api-docs.deepseek.com/guides/thinking_mode/),
[tool calls](https://api-docs.deepseek.com/guides/tool_calls/),
[JSON Output](https://api-docs.deepseek.com/guides/json_mode/),
[поддерживаемые модели](https://api-docs.deepseek.com/quick_start/pricing/).

**Реальные платные вызовы не проверены: в предоставленном окружении нет ключа.**
Тестовые провайдеры используются только в тестах; обычный сервер при отсутствии
ключа честно сообщает об этом и предлагает локальный поиск и формы.
До демонстрации жюри требуется пройти живой smoke-test, затем полный сценарий
создания/заполнения с реальной моделью и оценить задержку и качество ответов.

## Подключённые инструменты

Все 16 существующих инструментов доступны через единственную allowlist:

- Документы: `list_templates`, `get_template`, `create_document_project`,
  `get_document_project`, `list_document_projects`, `update_document_fields`,
  `validate_document_project`, `generate_document_docx`, `list_document_versions`,
  `get_document_artifact`.
- База знаний: `list_knowledge_documents`, `search_knowledge`,
  `get_knowledge_document`, `get_knowledge_section`, `list_knowledge_versions`,
  `verify_citation`.

Авторизация выполняется существующими сервисами по подписанной cookie; роль
вычисляется только серверным `principal_for`. Browser history, роль, HTML и UI-блоки
от модели не принимаются как полномочия или компоненты. Модель выдаёт ограниченный
JSON намерений. Формы, ссылки на артефакты и результаты проверок строит сервер.
Нормативный ответ требует цитаты, проверенной в текущем запросе; непроверенные
ссылки не публикуются. Открытие citation ведёт в существующий WorkspacePanel.

Внешний поиск, Python, SQL, shell и инструменты управления файлами не объявлены.
Корпоративные материалы базы знаний отфильтровываются до передачи провайдеру,
включая запросы администратора и перечисление редакций. Текст извлечённых источников
в системной инструкции обозначен недоверенными данными; это мера снижения риска
prompt injection, а не доказательство полной устойчивости любой модели.

## Семь модулей и единое состояние

Универсальный `DocumentChatForm` поддерживает все текущие модули:

| templateId | Документ |
| --- | --- |
| working-group-order | Рабочая группа |
| project-committee-order | Проектный комитет |
| internal-audit-order | Внутренний аудит |
| system-commissioning-order | Ввод информационной системы |
| records-officers-order | Ответственные за делопроизводство |
| handover-order | Приём и передача дел/имущества |
| local-act-order | Утверждение локального документа |

Поля, секции, обязательность, даты, select и многострочный ввод берутся из текущего
`Template.fields` (`FieldSpec`). Большие формы разбиты на раскрывающиеся секции.
Есть прогресс, ошибки рядом с полями, автосохранение, сохранение по кнопке,
валидация, настоящий DOCX-предпросмотр, генерация и скачивание без ухода из чата.
История браузера хранит ссылку на проект, а форма загружает актуальное состояние.

AI и форма используют один `DocumentProject` и одни API. Изменения формы сохраняются
в SQLite; перед AI-запросом клиент дожидается сохранения. Агент читает текущую версию
перед записью и передаёт только изменённые поля с `expectedVersion`. Полный редактор
при повторном открытии получает актуальный проект. Несохранённые локальные поля
хранятся в sessionStorage, сохраняются при перемонтировании и не отбрасываются при
конфликте. Пользователь видит свои и серверные значения и явно выбирает разрешение.

Генерация выполняется из копии оригинального модуля, не из текста LLM. Кнопка формы
просит подтверждение проверенной версии; сервер повторно проверяет её атомарно.
Для вызова через агента сервер создаёт подтверждение, привязанное к владельцу,
диалогу, проекту, версии и сроку 15 минут. Изменённую версию надо подтвердить заново.
Двойная генерация одной версии не создаёт второй артефакт.

## API-контракты

`POST /api/chat` требует session cookie и `X-CSRF-Token`:

```json
{
  "conversationId": "UUID",
  "requestId": "UUID, сохраняется при сетевом повторе",
  "message": "Создай приказ о вводе информационной системы",
  "syntheticOnlyAcknowledged": true,
  "history": [],
  "context": {"documentProjectId": null, "workspace": {"open": false, "tab": "sources"}}
}
```

Дополнительные серверные действия: `selectTemplateId` для явного выбора из каталога,
`confirmActionId` для подтверждения подготовленной генерации. Роль/owner не принимаются.
`history` оставлен для совместимости, но в контекст модели берётся серверная история.

`ChatResult` включает `conversationId`, `requestId`, `text`, типизированные `blocks`,
`sources`, `documentProjectId`, `provider`, `model`, `usage`. Блоки: `citation`,
`template_suggestions`, `document_form`, `document_card`, `document_preview`,
`validation_result`, `task_progress`, `clarification`, `download_artifact`.
Существующий `working_group_wizard` продолжает отображаться в старых диалогах.

`GET /api/chat/config` показывает только публичную конфигурацию.
`GET /api/chat/{conversationId}/requests/{requestId}` даёт реальные статусы инструментов.
`GET /api/chat/{conversationId}/history` возвращает публичную историю владельцу.
Раскрытия tool transcript и reasoning в этих endpoints нет.

`document_form` содержит реальные `projectId`, `templateId`, `projectVersion`, `title`,
`status`, `fieldSpecs`, `values`, `validation`, `editable`, `actions`; React повторно
загружает проект с авторизацией, а не доверяет сохранённой копии полей сообщения.

## Ключ и запуск

Добавьте секрет только в серверный `.env` локально или в закрытый
`/etc/regula/regula.env` на VPS (права 600). Образец — `.env.example` или
`deploy/regula.env.example`. Не используйте переменные `VITE_*` для ключей.

```dotenv
AI_PROVIDER=deepseek
DEEPSEEK_API_KEY=
DEEPSEEK_MODEL=deepseek-v4-pro
DEEPSEEK_BASE_URL=https://api.deepseek.com
AI_THINKING=1
AI_MAX_TOOL_STEPS=16
AI_REQUEST_TIMEOUT=90
AI_MAX_OUTPUT_TOKENS=4096
AI_MAX_MODEL_CALLS=12
AI_MAX_TOTAL_TOKENS=80000
AI_MAX_CONTEXT_CHARS=100000
AI_REQUESTS_PER_HOUR=30
```

В пустое значение `DEEPSEEK_API_KEY` вставьте выданный провайдером ключ в закрытом
файле на сервере. Не помещайте его в PR, frontend, команды общего чата и логи.
После изменения перезапустите только API с тем же постоянным томом. Для локального
Compose: `docker compose up -d --build`; для VPS используйте существующий rollout
с закреплёнными образами. Не удаляйте том и не запускайте destructive migrations.
Локальный uvicorn должен получить переменные окружения (или `--env-file`, если
установлена поддержка dotenv); сам Python-модуль не читает `.env` автоматически.

В чате отображается облачная обработка DeepSeek. Перед облачным запросом пользователь
подтверждает использование разрешённых синтетических материалов. Это необходимо и
для пользовательского текста/полей проекта: backend не может надёжно определить
конфиденциальность произвольного свободного текста. Реальные корпоративные документы
во внешний API передавать нельзя; до их подключения нужна отдельная проверка и разрешение.

## Ограничения и отказоустойчивость

Лимиты ограничивают шаги, обращения к модели, размер контекста/результата, output tokens,
совокупный token budget и время обработки. Подсчитывается usage, в логах — только
число вызовов/токенов/инструментов и длительность. Нет автоматического платного retry.
Rate limit хранится в SQLite: 30 запросов/час на сессию, общий предел — десятикратный.
Смена cookie не обходит общий предел. Для публичного развёртывания нужен также
существующий контроль доступа на прокси; анонимная сессия не заменяет корпоративную аутентификацию.

Запросы и инструменты имеют durable journal. Повтор с тем же requestId возвращает
сохранённый результат, иные аргументы отклоняются. Одновременные запросы одного
диалога не запускаются. После аварии начатая операция автоматически не повторяется:
клиент получает `request_interrupted_check_project`; состояние надо проверить в
каталоге проектов. Это предотвращает повторный побочный эффект, но не означает
распределённую транзакцию между журналом, диском и генератором DOCX.

Временный сбой провайдера не останавливает сайт, FTS5, формы и полный редактор.
Если проект успел создаться до сбоя, форма остаётся доступной. Отсутствие ключа не
подменяется демо-ответом модели: доступны реальный FTS5 и явный выбор модуля.
Тексты/шаги модели не стримятся; есть опрос реального серверного журнала выполнения.
Формальная проверка реквизитов не является юридическим заключением.
Анализ загруженного пользовательского файла по содержимому не реализован; имя файла
не выдаётся за результат анализа. Для него нужны безопасная загрузка/лимиты DOCX ZIP,
разбор текста, отдельный provenance и формальные правила проверки — отдельный этап.

История и private reasoning находятся в той же серверной SQLite, как и проекты.
Защитите том и резервные копии существующими серверными правами; не публикуйте БД.
Политика автоматического удаления истории пока не реализована.

## Проверка без оплаты

```bash
python -m pytest -q api/tests
npx tsc -b
npm run build
# Сначала запустите отдельный test-only API с временным REGULA_DATA_DIR:
REGULA_AGENT_BROWSER_TEST=1 AI_PROVIDER=local_qwen QWEN_MODEL=scripted-test \
  REGULA_DATA_DIR=/tmp/regula-agent-browser uvicorn api.tests.agent_browser_app:app --port 8000
# В другом терминале:
npm run dev
npx playwright test -c playwright.agent.config.ts
# Обычный сервер без ключа: прежние e2e и local fallback
npm run test:e2e
npm run test:viewer
# Compose: существующий scripts/compose-smoke.py плюс конфигурации deployment
```

Тестовый ASGI-модуль требует явного `REGULA_AGENT_BROWSER_TEST=1`, не импортируется
обычным backend и не выбирается production-командой образа. Test provider выдаёт
воспроизводимые tool calls; поиск, БД, редактор и DOCX в этих тестах настоящие.

Opt-in проверка **с платным запросом** в одноразовой БД:

```bash
# Секрет заранее должен быть в окружении; не выводите его в терминал.
REGULA_LIVE_AI_SMOKE=1 PYTHONPATH=. python scripts/agent-live-smoke.py
```

Smoke требует реальный ключ, проверяет поиск → п. 2.1 → проверенную citation и
создание/заполнение модуля информационной системы. Печатает только метрики.
Затем в браузере: «Создай приказ о вводе информационной системы» → заполнить недостающие
поля вручную/через диалог → «Проверить заполнение» → «Сформировать DOCX» → подтверждение
→ «Скачать DOCX». Проверьте оригинальный файл и сохранение после перехода в полный редактор.

## Переход на локальную Qwen и VPS

Выберите `AI_PROVIDER=local_qwen`, задайте `QWEN_BASE_URL`, `QWEN_MODEL` и при
необходимости `QWEN_API_KEY`. Адаптер обращается к `/chat/completions` совместимого
сервера; бизнес-сервисы, allowlist и frontend не меняются. Дополнительные настройки
thinking для конкретного Qwen inference-сервера пока не навязываются.

Перед миграцией обязательно проверить: схемы и JSON аргументы tool calling,
последовательные/параллельные calls и tool_call_id, контекст и reasoning-формат,
следование JSON-контракту, русский язык/точность реквизитов и дат, поиск и проверку
цитат/редакций, отказ от неизвестных требований, injection/ACL, задержку, throughput,
пиковую память inference-хоста, восстановление после сбоев и все сценарии приёмки.
Срок миграции до этих проверок не оценивается.

На VPS Ubuntu 26.04 (2 vCPU, 4 ГБ RAM) размещаются только FastAPI-оркестратор,
SQLite и nginx/Caddy. Модель на VPS не устанавливается. Лимиты памяти существующего
Compose сохранены; новые таблицы создаются аддитивно. Перед rollout нужен backup
существующего постоянного тома. Конфигурация nginx допускает ответ агента до 300 секунд.

  приватность reasoning, ACL/корпоративные материалы, неизвестные поля/редакции,
  подтверждения, сетевые повторы, параллельная генерация, лимиты и сбои провайдера.

- Docker: оба образа собраны; isolated Compose поднят и проверен через nginx;

  3 оригинала базы знаний, все 7 DOCX и границы multipart 20/22 MiB.
- Формы визуально проверены при ширине 1440 и 390 пикселей.
- Реальный DeepSeek API: **не проверен, ключ не предоставлен**. Это остаётся
  обязательным условием перед демонстрацией AI перед жюри.

## Краткие ответы для сотрудника

В тексте чата используются русские названия документов и реквизитов. Идентификаторы
шаблонов и названия инструментов остаются в серверном контракте. При выборе документа
показывается один каталог с кнопками; текст модели не повторяет список и вопрос выбора.
Данные формы и точные выдержки источников не проходят через очистку текста ответа.

После успешного создания/изменения краткое резюме строится из подтверждённого состояния
DocumentsService: созданный черновик, реально изменённые реквизиты, прогресс и следующий
шаг. Оно не может объявить все поля заполненными на основании слов модели. Замечания
используют подписи FieldSpec, а все 16 операций имеют русские названия. История действий
свёрнута, повторяющаяся справка о статусе шаблонов вынесена под каталог один раз.
HTML/SVG, блоки программного кода и технические имена очищаются в тексте помощника;
для старых диалогов действует дополнительная обработка при отображении. Исходный
текст пользователя, реквизиты и проверенные цитаты сохраняются без изменений.
